# Kiosk production planning

Decides how much sushi to make each morning, for a one-person kiosk inside a
ShopRite in Maryland. Everything is made fresh, has a shelf life under 24 hours,
and whatever does not sell is discarded.

Over the 116 recorded days in the seed data, **34.8% of production was thrown
away** — 2,455 units of 7,046, about **$57/day** of ingredients. That is the
number this system exists to reduce.

**Current status:** the deployed rule is the **per-roll rule**
([below](#the-per-roll-rule-deployed)): make each roll whose chance of selling
beats its break-even, cost ÷ price, with sell-outs read as "at least". Over
Jun 5 – Sep 21 it is about level with the operator's own numbers on profit and
ahead of the old same-weekday quantile, which read every sell-out as the most
that could have sold. [Why the old models failed](#what-does-not-work-and-why)
is still the most useful section of this document.

---

## 1. The model

This is a newsvendor problem. One decision per item per day, made before demand
is known, with asymmetric consequences: make too few and you forgo a sale, make
too many and you bin the ingredients.

For a quantity `q` against true demand `D`:

```
cost(q, D) = c_o · max(0, q − D)   +   c_u · max(0, D − q)
             \___ overproduction __/     \___ underproduction __/
```

The quantity minimising expected cost is the **critical ratio** quantile of the
demand distribution — not the mean, not the median:

```
q* = F⁻¹(τ),    τ = c_u / (c_u + c_o)
```

### The two costs, measured

**Overproduction.** Waste is counted the *morning after* the business day it
belongs to. By then the 19:00 markdown window has long closed, so anything that
cleared at a discount is already inside `sold`, and a unit that reaches the bin
earned nothing:

```
c_o = unit_cost − salvage = unit_cost        (salvage = 0)
```

The seed spreadsheet assumed `salvage = $1.50`, which is equivalent to assuming
~21% of leftovers clear at markdown. Given when the count happens, that was
double-counting: those units are already in `sold`.

**Underproduction.** A sale you could not make costs its contribution margin:

```
c_u = effective_price − unit_cost
```

`effective_price` is not list price. Wednesdays run buy-2-get-1, multiplying the
realised price by ⅔.

### The identity that falls out

With salvage at zero the ratio collapses to the gross margin ratio:

```
τ = c_u / (c_u + c_o) = (p − c) / p = 1 − c/p
```

There is no separate quantity to estimate. The ratio *is* the margin, which
means correcting a price or a recipe reprices every recommendation downstream
automatically. `analysis/costs.py` raises rather than returning a number when
`c_o ≤ 0` — at that point overproducing is free, the newsvendor says make
unlimited stock, and the binding constraint is labour and case space instead.

### Measured ratios

Costs come from a per-item bill of materials, not a blanket average. The
spreadsheet's flat `$2.75` hid a **4× spread**:

| | price | unit cost | τ | τ (Wednesday) |
|---|---|---|---|---|
| `spicy crab` | 6.99 | 1.17 | **0.833** | 0.749 |
| `cali roll` | 6.99 | 1.34 | 0.808 | 0.712 |
| `salmon avocado` | 7.99 | 2.09 | 0.738 | 0.607 |
| `poke` | 13.99 | 3.28 | 0.765 | 0.648 |
| `sashimi red` | 13.99 | 4.80 | **0.657** | 0.485 |

Across 42 items: unit cost **$1.17–$4.80** (mean $2.50), τ **0.612–0.853**.
Cheap high-margin rolls should be produced more aggressively than a flat ratio
suggested; expensive fish items less.

> **All ingredient costs are estimates awaiting correction.** They are
> effective-dated in the schema, so correcting one is an `INSERT`, not a
> migration.

## 2. The central problem: censored demand

`sold` is derived, never observed:

```
sold = made + refill − wasted
```

When `wasted = 0` the item sold out and all we know is `D ≥ supply`. **48.8% of
item-days are censored this way. 19 of 42 items sell out on more than half their
days.**

This is not a nuisance. It is a feedback loop, and the seed spreadsheet was
caught in it: its recommendation was built from `sold` one week prior, `sold` is
capped by production, and the recommendation then set production. An item that
sold out got anchored at its own ceiling indefinitely. `tornado shrimp tempura
roll` sold out 72% of its days; `spicy tuna inari` 68%, `spicy crab inari` 67%.
Those items were being quietly starved.

Stated plainly:

> **You cannot learn how much more you should have made, from data generated by
> making that much.**

### How the backtest stays honest about it

A harness that quietly substitutes `D = sold` makes underproduction look free on
exactly the sold-out days, and so systematically prefers policies that make
less — a bias pointing straight at the question being asked.

The structural fact that rescues the comparison: on a sold-out day, for two
quantities **both ≤ supply**, the unknown demand above supply adds an *identical
constant* to both costs.

```
q ≤ supply ≤ D  ⟹  cost(q) = c_u(D − q) = c_u(D − supply) + c_u(supply − q)
                                          └─ unknown, but identical ─┘
```

So their difference is exactly identified with no assumption. Only when a policy
recommends *above* supply on a sold-out day is the outcome genuinely unknown.
Every result therefore carries an **`unidentified_share`** — how much of the
score rests on demand nobody observed. There is also a sensitivity sweep
(`censored_demand_factor`), explicitly documented as *not a measurement*.

## The per-roll rule (deployed)

`analysis/rollchance.py`, ported to the app in `web/src/lib/model.ts` and held
to it by shared cases (`web/src/lib/fixtures/roll_chance_cases.json`, generated
by `tests/fixtures/make_roll_chance_cases.py`, replayed by both test suites).

**The rule.** For roll *k* of an item, estimate `S(k)` — the chance it sells —
and make it when `S(k) ≥ cost ÷ price`. That is the critical fractile read one
roll at a time: roll *k* earns its price if it sells and costs its cost either
way, so it pays exactly when `price · S(k) ≥ cost`.

**The chances.** `S(k) = g(0)·g(1)·…·g(k−1)`, where `g(j)` is "the next roll
sold, given the ones before it did" — observed on every day that made at least
`j+1` and sold at least `j`, sold-out or not. That is the Kaplan–Meier
product-limit estimator on whole units, and it is what makes a sell-out usable:
it says rolls 1–3 sold and nothing about roll 4, which is exactly what it
contributes. Days are weighted (same weekday 1.0, others 0.3; half-life 3
weeks), and each `g(j)` is pulled toward 0.5 — lightly (one day's weight) for a
roll made nearly every day, harder (five days') for a roll made only sometimes,
because the operator makes extra on days they expect to be busy and that record
flatters itself.

**The risk.** A roll above the most made lately is made only if that most sold
out recently and the estimate still clears break-even — and never more than one
above it. The 0.5 is anchored on a measurement: when the operator went above
their usual and the usual would have sold out, the next roll sold **57%** of the
time in the first half of the record and **58%** in the second.

**How it was chosen.** On profit, scored so that nothing is invented
(`analysis/evidence.py`): exact wherever the rule made no more than was made or
the day had leftovers — a roll added on a leftover day is a known failure — and
a range only for rolls above supply on a sold-out day. About a hundred settings
were scored on Jun 5 – Jul 31 under two assumptions for those unknowable rolls
(58% and a pessimistic 45%), and the choice was checked on Aug 1 – Sep 21.

Profit is after the middle man's 20% of every sale
(`tools/run_backtest.SALE_SHARE`), which raises every break-even by a quarter.

| per day (`python tools/compare_rules.py`) | made | left over | profit |
|---|---|---|---|
| operator, Jun 5 – Sep 21 (exact) | 61.2 | 21.7 | **$135.88** |
| old same-weekday quantile | 50.8 | ~16.1 | ~$128.94 [121.88 – 135.89] |
| per-roll rule | 60.4 | ~22.3 | ~$137.15 [115.73 – 154.69] |
| operator, Sep 1 – 21 (exact) | 69.5 | 26.0 | **$145.03** |
| per-roll rule, Sep 1 – 21 | 63.5 | ~22.5 | ~$149.67 [132.97 – 162.22] |

`~` is the estimate (rolls nobody could observe sell at the measured 58% given
the one before did); brackets are none-sold and all-sold. **The per-roll rule is
not proven better than the operator** — the gap is inside the range. What it is
proven to fix is the old rule's starving of sell-out items. In September its
exact gains are the trims — tri volcano (40 made, 23 left), both sashimis,
lobster volcano, tuna avocado — its estimated gains are test rolls on the
inaris, crab volcano and rainbow tuna, and the operator beats it on lobster
tuna sandwich and crunchy spicy tuna.

References: Arrow, Harris & Marschak (1951) for the critical fractile; Kaplan
& Meier (1958); Beran (1981) for the weighted, conditional form; Huh,
Levi, Rusmevichientong & Orlin (2011), *Operations Research* 59(4), and Huh &
Rusmevichientong (2009), *Mathematics of Operations Research* 34(1), for rules
that learn from censored sales and provably converge; Ding, Puterman & Bisi
(2002), *Operations Research* 50(3), for why, when sales are censored, the best
amount is higher than the one that looks best today.

## 3. Backtest methodology

`analysis/backtest.py`. For each evaluation day, in chronological order:

1. Build a `History` containing **only** observations strictly before that day.
2. Ask each policy for a quantity.
3. Score it against what actually happened.

**Scored in dollars of realised cost, never RMSE.** A squared-error metric picks
the conditional mean; the newsvendor optimum is a quantile. A test asserts this
directly: on synthetic demand `U{0,20}` with τ = 0.75, the harness must rank
`q=15` best, not `q=10`. A second halves the margin and asserts the optimum
*moves down*, proving the cost model drives the result rather than decorating it.

**Leakage is prevented structurally, not by discipline.** A policy receives a
pre-sliced `History` and holds no reference to the full dataset. The strongest
test corrupts every observation after day 20 to garbage and asserts decisions on
days ≤ 20 are byte-identical.

Feature construction has its own causality test, because a trailing mean
computed across the whole training block would leak the future *inside* the
training set — a leak the harness cannot detect.

The harness has **34 dedicated tests**. It is the component whose bugs would
silently invalidate every downstream result, so it is tested adversarially
rather than for coverage.

## 4. Results

89 walk-forward days, 2026-06-05 → 2026-09-01, 28-day warm-up.

| Policy | Total $ | $/day | Waste $ | Stockout $ | vs baseline |
|---|---|---|---|---|---|
| `same_weekday_mean` *(baseline)* | 7,493 | 84.19 | 2,424 | 5,069 | — |
| **`same_weekday_quantile` (deployed)** | **5,961** | **67.74** | 3,302 | 2,659 | **−14.1%** |
| `pooled_poisson` | 7,886 | 88.61 | 6,586 | 1,299 | +3.1% |
| `per_item_poisson` | 7,999 | 89.88 | 5,498 | 2,501 | +9.9% |
| `operator_actual` — the human | 4,321 | 48.55 | 4,321 | 0 | −45.2% |

Two things worth reading carefully.

**The naive baseline loses badly, and why is informative.** 68% of its cost is
*stockouts*. It averages `sold`, `sold` is censored on half the item-days, so it
systematically under-forecasts and starves exactly the items that sell out.
Moving from the mean to the critical-ratio quantile recovers about a third of
the gap to the operator.

**The operator's zero stockout cost is structural, not a finding.** Demand is
measured by a lower bound that equals their own supply, so on every sold-out day
they score as having hit demand exactly. Their stockouts are invisible to the
harness *by construction*. The comparison between policies remains valid (see
the identity above), but the harness **penalises any policy producing more than
the operator did** — which is precisely what a better model would want to do.

Sensitivity to that, with only the first row measured:

| If true demand on sold-out days ran… | baseline | quantile | operator |
|---|---|---|---|
| = supply (measured) | 7,493 | 5,961 | **4,321** |
| 10% above | 8,829 | 7,104 | **5,852** |
| 25% above | 10,832 | 8,820 | **8,148** |
| 50% above | 14,195 | **11,739** | 11,975 |

**The ranking flips at +50%.** Honestly: *under what can be observed the
operator is clearly ahead; if they have been running out substantially more than
the data can show, the simple rule is already better.* Which of those is true is
not knowable from this data — it is knowable from a few weeks of deliberate
overproduction on the heavy sell-out items, which is
[the recommendation below](#the-one-change-that-would-unlock-this).

Only the first row is measured. The rest is sensitivity analysis and is labelled
as such in the code.

## 5. What does not work, and why

Phase 4 specified per-item quantile regression at the critical ratio. **It does
not run on this data**, for a precise reason.

Powell's censored quantile regression learns only from observations whose fitted
quantile lies *below* that day's censoring limit. The limit is the quantity
supplied, and supply sits near the **median** of demand. For τ ≈ 0.75 almost
every observation is above the frontier and nothing is left to fit:

```
per_item_cqr    model    10  fallback 2551  (0% modelled)  converged  5 / not 613
pooled_cqr_log  model     0  fallback 2561  (0% modelled)  converged  0 / not  56
```

Their apparent −10.2% *was the fallback's score*. The estimator is not failing;
it is correctly reporting that the target is not identified.

**Censored Poisson regression** (`analysis/countreg.py`) can extrapolate above
the frontier, and does fit — 98% modelled. It is worse, and the diagnostics say
why: dispersion **0.59** (0.79 on uncensored rows alone) means demand has *less*
variance than Poisson assumes, so the fitted tail is too fat and the model
overproduces. Underneath that, on days that did not sell out it predicts **1.76
units against actual demand of 0.90** — it corrects the level for censoring but
cannot tell a sell-out day from a waste day.

**The feature ablation confirms it:**

| Features | Params | Total $ | vs baseline |
|---|---|---|---|
| trailing level only | 1 | 8,140 | +6.6% |
| level + day-of-week | 7 | 8,079 | +5.6% |
| level + dow + trend | 8 | 7,892 | +3.1% |
| day-of-week only | 6 | 8,151 | +6.7% |

A 3% spread across feature sets differing 8× in parameter count. Day-of-week,
trailing level and trend explain almost nothing about *which* days an item sells
out. No feature earned its place, so none were added.

### The one change that would unlock this

*Now built into the per-roll rule as its test roll — one above the most made
lately, only after that most sold out.* The original recommendation:

The binding constraint is the data, not the algorithm. **Deliberate
exploration:** on the worst offenders — `crunchy spicy crab volcano` (95% sold
out), `tornado shrimp tempura roll` (72%), `spicy tuna inari` (68%) — make 2–3 extra for
a few weeks. If they sell, you have discovered demand the data has never been
able to show. If they do not, you have bounded it for a few dollars a day.

## 6. Architecture

```
 workbook.xlsx ─┐
                │  tools/profile_workbook.py    read-only structural profile
                │  tools/extract_workbook.py    → reviewable CSVs + exceptions
                │  tools/import_seed.py         → Postgres, idempotent
                ▼
           Postgres (Supabase)                  db/schema*.sql
                │
    ┌───────────┴────────────┐
    ▼                        ▼
 analysis/                 web/  (React + TS, Vercel)
   costs   backtest          offline-first, IndexedDB
   policies models           morning waste count → review → today's plan
   prepsheet scorecard       templates per weekday, effective-dated
   health  alerting
    │
    └── tools/jobs.py   ingest · retrain · prep · score · status
```

**Data model.** Surrogate item IDs, never names. Item attributes and ingredient
prices are effective-dated — a correction is an `INSERT`. The daily log is
append-only, enforced by a trigger; corrections are new rows, and
`business_date` is separate from `recorded_at` because **waste is counted the
morning after the day it belongs to**. Getting that wrong files a day's waste
against the wrong date.

Sales are a **view**, not a table: fully determined by `made + refill − wasted`,
so a table would be a second thing owning the same fact.

**The app** works with no server and no wifi. Writes hit IndexedDB and return
immediately; queued mutations carry a client UUID that becomes `source_ref`, so
the existing `(source_ref, value_hash)` constraint dedupes replays for free.
Templates are what make the form usable in under a minute — thirty items typed
is three minutes, four corrected is one.

**Scheduling.** `tools/jobs.py`, driven by GitHub Actions cron. Ordering is
deliberate: ingest → score → **sheet last**, with `if: always()` throughout, so
no upstream failure can deny the operator a sheet.

### Graceful degradation

Verified by breaking it: with state deleted and ingest pointed at a missing
directory, the sheet still printed every number and said —

```
! PIPELINE: Last ingest attempt failed: FileNotFoundError: ...
! PIPELINE: Ingest has never completed.
```

An operator at a kiosk at 5am is not helped by an error page. Presenting
yesterday's answer as today's without saying so is worse.

### Alerting

`Notifier` is a two-method protocol; `WebhookNotifier` POSTs JSON to a URL, so
ntfy.sh / Pushover / Telegram / Slack are a config value, not a dependency.
Standard-library `urllib` only — an alerting path that can fail to import is not
alerting. Conditions alert once then cool down for 12h, and a cleared condition
forgets its cooldown so a recurrence alerts again.

## 7. Limitations and failure cases

**Modelling**

- *Demand above supply has never been observed on half the item-days.* Every
  recommendation for a heavy sell-out item is a **floor**, not an estimate. The
  prep sheet says so per line.
- *The harness scores a single-shot decision.* The real process has an afternoon
  refill (411 units across the period). A mid-day top-up genuinely reduces
  stockout risk in a way the model cannot credit, so stockout costs are somewhat
  overstated for everyone.
- *117 days is thin.* Median 15 same-weekday observations per item; the
  empirical quantile at n=8 is coarse, and the quantity floor exists partly
  because of that coarseness.
- *No fitted model is deployed.* The banner says so. This is the honest state,
  not a placeholder.

**Economics**

- *Ingredient costs are estimates.* They set τ, which sets every quantity.
  Correcting them is the highest-value input available.
- *B2G1 is modelled as a flat ⅔ multiplier.* If it is really "cheapest of three
  free", the discount is smaller on expensive items and Wednesday's ratios are
  too pessimistic for sashimi and poke.
- *Markdown share defaults to 0.* Unmeasurable from the seed data; sensitivity
  is small (τ 0.725 → 0.698 across 0–30%).

**Data**

- *The seed workbook's revenue column is fiction.* `Total Revenue` was computed
  from a wildcard PLU lookup where **14 of 43 items fell through to a flat $10**
  and `cali roll` was priced at $13.99 instead of $6.99. There is no observed
  revenue anywhere in the source. All figures here derive from hand-counted
  made / refill / waste.
- *17 of 146 sheets disagree with their own totals row* — the spreadsheet's
  `Total Made` formula summed the refill column only to row 38 while items ran
  past it. Item rows are authoritative; the reconciliation report explains every
  discrepancy rather than netting them out.
- *Four rows record more waste than supply* (unrecorded refills). Demand is
  clamped at zero and the inconsistency flagged.
- *Zeros in the seed are inferred, not attested.* A blank waste cell means zero.
  The app requires an explicit confirmation, so data collected from now on is
  attested; the seed's 1,659 sellouts are not.

**Operational**

- *The alert path has not been exercised against a real service.* Set
  `ALERT_WEBHOOK_URL` and run `jobs.py status` to prove it end to end.
- *GitHub Actions cache is best-effort state.* Supabase `pg_cron` is the better
  home once the database is provisioned.
- *The recommendation rule exists twice* — Python for the validated path,
  TypeScript so the app works offline. Cross-implementation tests pin them
  against shared fixtures whose expected values were produced by running the
  Python implementation.

## 8. Running it

```bash
pip install openpyxl numpy scipy            # statsmodels for tests only
python tools/extract_workbook.py "workbook.xlsx" --out data
python tools/seed_recipes.py --out data     # draft costs — correct these
python tools/import_seed.py --dry-run --reconcile "workbook.xlsx"
python tools/import_pdf_days.py data/<sheet>.txt --write   # days that arrive as a PDF

python tools/compare_rules.py               # the per-roll rule vs the old rule vs you
python tests/fixtures/make_roll_chance_cases.py  # after changing the rule: regenerate the app's cases
python tools/run_backtest.py                # Phase 3 scorecard
python tools/run_phase4.py                  # model comparison + ablation
python tools/jobs.py prep                   # morning sheet
python tools/jobs.py score                  # rolling 30 days
python tools/jobs.py status                 # health + alerting

python tools/predict_day.py                 # write today's prediction down, BEFORE the day
python tools/score_prediction.py 2026-09-22 # tomorrow: score it, update docs/predictions/TALLY.md

cd web && npm install && npm run dev        # the app
```

The app needs no key and no server. Weather is opt-in: type a ZIP into
Setup -> Weather and it backfills every day already on record, after which the
home screen leads with today's sky and what it points to.

```bash
cd web
npm test                                    # unit tests
npm run build                               # tsc + vite + stamp the service worker
npx vite preview --port 4173 &              # the harnesses below need this
npm run flow                                # the morning loop, end to end
npm run wx                                  # home and the sheet quote the same %
npm run wx:verify                           # the import, and that the sync settles
npm run wx:shots                            # the weather card, light and dark
```

Tests: `python -m pytest tests/ -q` (**227**) and `cd web && npm test` (**192**).

The operator's real workbook and all extracted data stay out of version control;
`tests/fixtures/fixture.xlsx` is a committed, anonymised stand-in that reproduces
every structural hazard found in the real file.
